# BLH Hunter v2 — durable recon workspace

The v2 pipeline runs alongside the legacy API/UI. It uses a separate database by
default (`blh_v2.db`), so testing v2 does not migrate or modify `blh_hunter.db`.
The existing web app exposes the new workspace at `/v2` and API at `/api/v2`.
For v2-only operation use `lazy_dorking.v2.app:app`.

## Local setup (PowerShell)

```powershell
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-v2.txt
.venv\Scripts\python -m playwright install chromium
.venv\Scripts\python -m uvicorn lazy_dorking.v2.app:app --host 127.0.0.1 --port 8001
```

Start a worker in a second terminal, from the same project directory:

```powershell
.venv\Scripts\python -m lazy_dorking.v2.worker
```

Open http://127.0.0.1:8001/v2. A scan remains QUEUED until a worker is running.
The native HTTP mode needs only `requirements.txt`; Crawlee and browser modes need
`requirements-v2.txt`. Browser mode also needs Chromium installed for the worker's user.

## PostgreSQL and Celery

Set `BLH_DATABASE_URL` identically for API, worker and migration commands:

```text
postgresql+psycopg://blh:URL_ENCODED_PASSWORD@localhost:5432/blh
```

The schema is initialized by the API or `Store.init()`. The initial schema uses
SQLAlchemy's portable types, JSON and cascading foreign keys. Future schema
changes require versioned migrations; `create_all` does not alter existing tables.

For the included isolated Compose stack, set `BLH_DB_PASSWORD` and a matching
`BLH_DATABASE_URL` whose hostname is `db`, then:

```text
docker compose -f compose.v2.yml up --build -d
```

The API is bound to loopback port 8001. Use your existing Tailscale/private proxy.
The amd64 image includes pinned Subfinder, gau, Katana, PD httpx, Nuclei and
Gitleaks releases, verified against their upstream checksum manifests, plus
jsluice built from a pinned commit. Versions are recorded in
`deploy/install_tools.py` and `Dockerfile.v2`. Set `BLH_RELEASE` to the deployed
commit to tag the shared API/worker/scheduler image.
The app has no account/authentication layer; do not expose it publicly.
PostgreSQL and Redis have no published host ports. The old application on 8000
is not replaced. No production deployment is performed by local setup.

Without Compose, initialize the schema via API startup, set `BLH_REDIS_URL`, and run:

```text
celery -A lazy_dorking.v2.tasks:app worker --loglevel=INFO --concurrency=2
celery -A lazy_dorking.v2.tasks:app beat --loglevel=INFO
```

Use one Beat scheduler. Direct `python -m lazy_dorking.v2.worker` is the supported
development path on Windows. Redis messages only trigger work: persistent job
state remains in SQL even if Redis is lost. A job is leased for 120 seconds,
renewed every 2 seconds, and fenced by a unique token. Worker loss may repeat an
unfinished HTTP request; database results/checkpoints are committed atomically.

## Engine ownership and scope

BLH owns the persistent frontier, round-robin host selection, selected-platform
coverage, page budget and scan lifecycle. Crawlee consumes a leased page without
using its own persistent request queue. Its in-memory queue is disposable.
This first implementation favors correctness over throughput: the direct worker
executes one job at a time; Celery can run multiple worker processes.

HTTP is attempted first. Browser escalation is optional, budgeted and triggered
by sparse links plus app-shell markers. Browser requests are GET-only and scoped
to the target domain, including resources. Some sites relying on external CDNs
will consequently render incompletely. Source redirects outside scope are not
followed. External profiles/services are checked as targets, never crawled as
source pages. Response bodies are capped; validation stores metadata/hash, not
raw secrets or response bodies. Public-address checks are an additional filter,
not a substitute for network egress isolation against DNS rebinding.

Discovery providers: root URLs, scoped robots/sitemap, native Wayback/Common
Crawl, optional Subfinder, gau and Katana. Outside the Docker deployment, install
CLI tools separately on workers and pin their versions. Selecting a missing tool produces visible
failed jobs, not a silent fallback. gau cannot be selected together with native
archive providers. Katana is opt-in, bounded standard-mode discovery; its findings
pass through the same normalizer and source crawl. It does not yet stream external
target evidence directly into analyzers.

Every scan snapshots its configuration. Pages retain coverage per analyzer and
selection; coverage is calculated only from retained scan-owned records. URL
inventory is distinct from findings. A finding can have many source evidence
records. Previously known findings are labeled `is_new=false`, not new results.
Deleting a scan cascades its jobs/pages/URL history/evidence; findings survive
only while another scan references them. No deleted scan dedupe tombstones remain.

PAUSED means no new jobs dispatch and outstanding tokens are revoked; in-flight
network requests can take up to the heartbeat interval to cancel. COMPLETED
means all jobs finished or were intentionally skipped by budget. FAILED means
one or more jobs exhausted three attempts; partial results remain reviewable.
Cancellation and deletion reject late writes from old workers.

## Import existing data

Back up the source database first. Import reads a consistent SQLite snapshot and
does not write to the source. Default mode reports counts only:

```text
python -m lazy_dorking.v2.migrate blh_hunter.db
python -m lazy_dorking.v2.migrate blh_hunter.db --apply
```

Deterministic legacy scan IDs make repeated imports idempotent. BLH/BAC/CRED
results and crawl coverage are imported with legacy source attribution. Existing
legacy statuses are preserved as historical evidence with low confidence.
Legacy in-memory queues cannot be reconstructed: unfinished legacy scans are
imported as cancelled history, never automatically dispatched to network workers.

## Implemented and remaining

The production `/` homepage preserves the classic BLH, BAC, CRED, dashboard,
history, CSV export and scan controls. Its `/api/blh`, `/api/bac` and `/api/cred`
contracts now use the PostgreSQL-backed v2 jobs and Celery workers. `/v2` remains
an optional advanced workspace. Classic scans enable installed browser/JS tools,
Subfinder and gau (native archives when gau is unavailable); CRED also enables
redacted Gitleaks signals and the selected exposure templates. Katana remains
opt-in from the advanced workspace. Classic BAC dorking runs as durable jobs.
The old CRED brute-force checkbox never implemented active requests; it is now
explicitly disabled rather than silently ignored. Manual BLH status overrides
are retained separately from automated evidence and survive worker completion.

Implemented: persistent scans/jobs and token fencing; PostgreSQL/SQLite store;
direct worker and Celery dispatch; discovery adapters; Crawlee HTTP/browser;
HTML reference extraction; reusable BLH/BAC/CRED classification; conservative
validation; evidence, review status, paginated inventory and JSON export;
explicit legacy import and isolated deployment configuration.

Optional adapters are also implemented for jsluice URL extraction, Gitleaks
redacted secret signals, PD httpx host metadata and three repository-owned Nuclei
templates (exact discovered `.env`, `.git/config`, Swagger/OpenAPI URLs only).
These tools are disabled by default and must be installed on the worker. Set
`BLH_HTTPX_BIN` to the ProjectDiscovery binary path; the default name is
`httpx-toolkit` to avoid collisions with Python's `httpx`. Probing records metadata
without excluding the host's historical URLs on a failed probe. CLI adapter
parsing is fixture-tested. `deploy/verify_runtime.py` additionally exercises the
installed binaries and Chromium against local HTTP fixtures.
Gitleaks content is held in a temporary file during analysis, deleted afterward;
only rule IDs and line numbers enter persistent evidence. No credentials are tested.

Not yet implemented: calibrated platform-specific checkers for every social
platform, definitive provider-specific BAC public-access verification,
DNS intelligence and production throughput tuning. PD httpx currently probes
per host rather than bulk batches. Capability discovery reports executable
presence on the API host, not worker health or compatibility.
`reachable` does not prove a profile exists or a collaboration resource is public;
`accessible_candidate` does not prove that an exposure contains sensitive data.

## Validation

```text
python -m pytest tests/test_v2.py -q
python -m unittest test_main.py -q
```

Tests use isolated temporary databases and synthetic responses, not live targets.
Chromium is required for the browser fixture. To run the durable-store suite on
PostgreSQL, set `BLH_TEST_POSTGRES_URL` to a test PostgreSQL instance with schema
creation privileges. Each test creates and drops a separate `blh_test_*` schema.
Exercise PostgreSQL and Celery/Redis in staging before switching production traffic.

The worker uses the Chromium seccomp profile from
[Playwright](https://github.com/microsoft/playwright/blob/main/utils/docker/seccomp_profile.json)
to permit browser user namespaces while retaining Chromium sandboxing. Run
browser tests as the image's non-root `blh` user with this profile, matching the
worker's Compose configuration. Do not disable the browser sandbox to run tests.
